# 统一站点双模块项目 最终执行方案

## 1. 方案结论

本项目应定义为一个**统一网站**，包含两个**相互独立的核心业务模块**：

- 物流管理模块
- 电商模块

两者不是主从关系，也不是“物流系统服务于电商系统”的单向结构。  
真正准确的关系是：

- 两个模块在前台并列存在
- 共享统一账号体系
- 共享统一后台登录入口 `/admin`
- 在订单层存在有限关联：**电商订单可以生成物流单号，并在物流模块中查询**

## 2. 冻结后的业务定位

### 物流模块

- 当前主业务
- 目标是第一版即可正式上线运营
- 面向 B 端和 C 端客户开放报价、下单、查轨迹
- 由运营人员在后台审核与管理

### 电商模块

- 当前为轻量 MVP
- 目标是第一版可上线，但功能范围控制在最小可运营集
- 仅面向 C 端销售普通实物商品
- 支持商品展示、SKU 选择、下单、订单查看
- 支持电商订单生成物流单号并接入物流查询链路

## 3. 六轮需求对齐后的核心共识

### Round 1：系统关系

- 一个统一网站
- 前台包含两个独立模块：物流、电商
- 后台是同一个管理员登录体系

### Round 2：账号与角色

- 全站统一账号
- 账号本身不预设 B 端 / C 端身份
- 用户在报价和下单时，自行勾选本次货物属于 B 端货或 C 端货
- 后台为独立的 `/admin`

### Round 3：物流业务模型

- 业务主方向：**中国发往海外**
- 物流链路分为：
  - 头程：接收货物到目的国前
  - 尾程：海外本地派送
- 头程节点由运营人工录入
- 尾程通过固定海外物流服务商 API 创建订单并同步轨迹
- 头程 / 尾程只作为后端与后台管理模型，前台统一展示为常规物流信息

### Round 4：报价与下单

- 报价维度：`国家 + 城市 + 实际重 / 体积重取大`
- B 端与 C 端使用两套不同报价表
- 客户必须填写完整寄收件、地址、货物、申报和税务信息
- 报价表既要支持后台逐条维护，也要支持 Excel / CSV 导入导出

### Round 5：电商范围

- 电商只做 C 端
- 商品为普通实物商品
- 支持多规格 SKU，例如型号、鞋码
- 第一版不接在线支付，采用下单后人工确认
- 库存不自动扣减，人工维护
- 售后不做站内流程，统一跳转 WhatsApp / Telegram

### Round 6：正式版技术路线

- 前端：Next.js + React
- 后端：NestJS
- 数据库：PostgreSQL
- 数据层与对象存储：Supabase
- 前端部署：Vercel
- 文件存储：Supabase Storage
- 认证方式：邮箱 + 密码
- 前台页面文案支持：中文 / 英文 / 俄文
- 文件上传能力首期必须支持：
  - 商品图片
  - Banner 图片
  - 客户身份证 / 税号资料

## 4. 系统边界

## 4.1 前台客户站

前台应拆成两个一级业务入口：

- 物流服务
- 商城购物

### 物流前台能力

- 在线报价
- 在线创建物流订单
- 查询物流轨迹
- 管理自己的收件人信息
- 上传身份证 / 税号资料

### 电商前台能力

- 浏览商品
- 搜索 / 筛选商品
- 查看商品详情
- 选择 SKU
- 提交订单
- 查看订单
- 从电商订单查看对应物流单号

## 4.2 后台管理站 `/admin`

后台使用同一管理员登录，但内部明确拆成两大模块：

- 物流管理
- 电商管理

### 物流管理后台

- 物流订单审核通过 / 驳回
- 修改货物重量与尺寸
- 录入与维护头程物流单号
- 调用海外尾程 API 创建尾程订单
- 同步尾程单号
- 维护头程轨迹节点
- 自动拉取尾程轨迹
- 标记异常
- 标记签收
- 报价表管理
- 国家 / 城市配置
- 海外 API 配置
- 客户收件人信息查看
- 操作日志

### 电商管理后台

- 商品管理
- SKU 管理
- Banner / 内容管理
- 电商订单管理
- 将电商订单映射到物流订单

## 7. 技术执行路线

## 7.1 总体架构

建议采用：

- Next.js 承担前台与后台管理界面
- NestJS 承担独立业务 API
- PostgreSQL 作为核心业务数据库
- Supabase 承担数据库托管、对象存储与认证能力
- Vercel 承担 Next.js 前端部署

### 关键说明

由于你已经明确后端采用 `NestJS`，正式生产环境更合理的方案是：

- `Vercel` 部署 Next.js 前端
- `NestJS` 独立部署为 API 服务
- `Supabase` 提供 PostgreSQL、Storage、Auth

不建议把 NestJS 主后端强行塞进 Vercel 的 Serverless 运行模式，否则后期在文件处理、任务同步、第三方物流回调和后台稳定性上会比较吃力。

## 7.2 推荐实施顺序

- 确认标准报价模板

### Phase 1：基础工程

- 建立多语言框架

### Phase 2：物流主系统

- 物流下单系统

### Phase 3：电商 MVP

- 商品展示
- SKU 选择
- 下单流程
- 电商订单映射物流单

### Phase 4：后台补齐

- Banner 管理

## 8. 当前必须锁定的前置依赖

有两项会直接影响最终数据库和报价引擎实现：

- 海外尾程服务商 API 文档
- 你后续提供的标准报价模板

在没有这两项前，PRD 可以先完成结构设计，但报价规则表和 API 适配层只能先按可扩展方式预留。

## 9. 风险判断

### 风险 1：将“账号类型”和“货物类型”混淆

应对：

- 账号不分 B / C
- 每票订单单独选择货物类型
- 所有报价、字段校验、流程规则按订单维度生效

### 风险 2：物流头尾程状态脱节

应对：

- 明确头程与尾程为两段模型
- 头程节点人工维护
- 尾程节点 API 自动同步
- 前台展示统一时间线，但后台保留分段数据结构

### 风险 3：NestJS 与 Vercel 误配

应对：

- 前端和后端分离部署
- Vercel 只负责 Next.js
- NestJS 作为独立 API 服务部署

## 10. 最终建议

这次修正后，最稳的执行路径不是先做“完整商城”，而是：

1. 先把物流正式版做扎实
2. 再把电商做成能上线的轻量 MVP
3. 只保留“电商订单生成物流单号”这一条业务连接
4. 在技术上一次性用正式生产架构搭好，不再使用 `localStorage + mock-only` 的演示级方案

这才符合你现在的真实业务优先级和上线目标。
