# 统一站点双模块项目 技术 PRD

## 1. 文档目标

本文档定义一个统一网站中的两大业务模块：

- 物流管理模块
- 电商模块

目标是形成一套可直接上线运营的正式版方案，其中：

- 物流模块为正式版主业务
- 电商模块为正式版中的轻量 MVP

本文档覆盖产品范围、前后端职责、数据库方向、对象存储、认证、多语言、第三方 API 集成、后台模块与实施路线。

## 2. 项目定义

## 2.1 系统关系

本项目不是“物流服务于电商”的从属系统，也不是两个完全割裂的网站。准确关系如下：

- 一个统一网站
- 两个前台独立模块
- 一套统一账号体系
- 一个统一后台入口 `/admin`
- 两个模块在订单层存在有限关联：**电商订单可生成物流单号**

## 2.2 业务优先级

- P1：物流模块
- P2：电商模块

## 2.3 上线目标

- 第一版即面向真实业务上线
- 不采用演示型 `localStorage` 数据方案
- 后端、数据库、对象存储、认证都按正式生产架构设计

## 3. 用户角色

## 3.1 前台客户

统一账号登录，不区分账号级 B 端 / C 端身份。

用户在以下场景自行选择本次订单货物类型：

- B 端货物
- C 端货物

### 客户能力

- 邮箱注册 / 登录
- 创建物流报价与物流订单
- 查询物流订单
- 浏览商城商品并下单
- 查看自己的电商订单
- 管理自己的收件人信息
- 上传身份证 / 税号资料

## 3.2 管理员

- 使用 `/admin` 后台统一登录
- 同一管理员可管理物流与电商两大模块

### 管理员能力

- 审核 / 驳回物流订单
- 修改货物重量、尺寸等关键数据
- 录入头程物流单号与头程轨迹
- 创建尾程订单并同步尾程单号
- 拉取尾程轨迹
- 标记异常 / 完成签收
- 管理报价表
- 管理国家 / 城市配置
- 管理海外 API 配置
- 管理电商商品、SKU、Banner、订单
- 查看客户收件人信息
- 查看操作日志

## 4. 业务模块设计

## 4.1 物流模块

### 4.1.1 业务目标

支持中国发往海外的双段物流业务。

物流由两部分组成：

- 头程：从收货到目的国海关前后
- 尾程：目的国本地派送

说明：

- 头程 / 尾程仅作为后端、数据库与后台运营管理模型
- 前台不向客户显式展示“头程”或“尾程”概念
- 前台统一展示为常规物流状态与时间线

### 4.1.2 前台功能

#### 在线报价

客户输入：

- 本次货物类型：B 端货 / C 端货
- 目的国家
- 目的城市
- 重量
- 尺寸
- 件数

报价逻辑：

- 按国家 + 城市计算
- 实际重 / 体积重取大
- B 端和 C 端分别使用不同定价表
- 根据后续标准报价模板计算最终金额

输出：

- 报价金额
- 币种
- 计费重量
- 价格构成说明

#### 物流订单创建

客户必填字段：

- 发件人信息
- 收件人信息
- 国家 / 省市 / 邮编
- 货物名称
- 重量
- 尺寸
- 件数
- 申报价值
- 币种
- 身份证 / 税号

支持上传：

- 身份证资料
- 税号资料

#### 物流订单查询

客户可按订单号或物流单号查看状态和轨迹。

前台展示原则：

- 只展示统一物流状态
- 只展示统一轨迹时间线
- 不展示头程 / 尾程的内部拆分模型

#### 收件人信息管理

客户维护自己的常用收件人资料。

## 4.1.3 后台功能

#### 物流订单审核

- 审核通过
- 驳回
- 修正重量
- 修正尺寸

#### 头程管理

- 录入头程单号
- 录入头程轨迹节点

#### 尾程管理

- 调用固定海外物流 API 创建尾程订单
- 获取尾程单号
- 将尾程单号同步到头程 / 主订单视图
- 拉取尾程轨迹

#### 异常与完结

- 标记异常
- 标记签收

#### 配置管理

- B 端报价表
- C 端报价表
- 国家 / 城市配置
- 海外 API 配置

## 4.1.4 状态流转

标准物流状态链：

1. 货物接受
2. 转运至中转仓
3. 货物已发出
4. 运输中
5. 到达目的国海关仓库
6. 清关中
7. 清关完成
8. 尾程派送
9. 签收

补充状态：

- 审核中
- 已驳回
- 异常

### 状态来源

- 头程状态：后台人工录入
- 尾程状态：第三方 API 拉取

## 4.2 电商模块

### 4.2.1 业务目标

提供面向 C 端用户的轻量实物商品商城。

### 4.2.2 前台功能

- 商品列表
- 商品详情
- SKU 选择
- 加入购物车
- 提交订单
- 查看订单

### 4.2.3 商品模型要求

- 普通实物商品
- 支持多规格 SKU
- 示例：型号 + 鞋码

### 4.2.4 订单流程

- 不接在线支付
- 用户先下单
- 后台人工确认
- 电商订单可映射生成物流单号

### 4.2.5 当前不做

- 自动库存扣减
- 在线支付
- 站内退款 / 退货 / 售后

售后引导方式：

- WhatsApp
- Telegram

## 4.3 模块间关系

物流与电商在系统上相互独立，但存在一条明确的业务桥接：

- 电商订单创建后，可由后台创建关联物流订单
- 前台用户可在电商订单详情看到物流单号
- 用户可从电商订单跳转到物流查询

除此之外，两者不共享复杂业务流程，不以其中一方作为另一方的核心依赖。

## 6. 多语言范围

第一版仅做**前台页面文案多语言**：

- 中文
- 英文
- 俄文

不做：

- 后台多语言
- 商品内容多语言版本
- Banner 内容多语言版本

因此第一版多语言实现范围应控制在：

- 导航
- 按钮
- 表单标签
- 状态文案
- 提示文案

## 7. 文件上传范围

第一版必须支持以下上传：

- 商品图片上传
- Banner 图片上传
- 客户身份证资料上传
- 客户税号资料上传

建议全部存储到 `Supabase Storage`，并按业务桶分离：

- `product-images`
- `banner-assets`
- `customer-documents`

## 9. 技术选型

## 9.1 前端

推荐选型：

- Framework：Next.js App Router
- UI：React + TypeScript
- Styling：Tailwind CSS
- Animation：Framer Motion
- Icon：Lucide React
- i18n：`next-intl` 或同类成熟方案
- 表单：React Hook Form + Zod

### 选型原因

- Next.js 适合统一承载前台站点与后台管理端
- App Router 适合路由分区：物流 / 电商 / 后台
- Tailwind 能快速建立一致的运营后台与前台样式体系
- React Hook Form + Zod 适合复杂报价与下单校验

## 9.2 后端

推荐选型：

- Framework：NestJS
- API 风格：REST API
- 校验：class-validator / class-transformer
- 鉴权：基于 Supabase Auth 的 token 校验
- 文档：Swagger
- 定时任务：NestJS Schedule
- 第三方集成：独立物流 provider adapter

### 后端职责

- 认证鉴权
- 物流报价计算
- 物流订单管理
- 电商订单管理
- 第三方尾程 API 集成
- 文件元数据管理
- 操作日志记录

## 9.3 数据库

推荐选型：

- Database：PostgreSQL
- 托管：Supabase Postgres

### 选型原因

- 物流订单、报价表、SKU、操作日志都更适合关系型模型
- PostgreSQL 对复杂筛选、约束、索引、JSON 扩展更稳定
- 与 Supabase 生态整合顺畅

## 9.4 认证

推荐方案：

- Supabase Auth 提供邮箱 + 密码认证
- Next.js 前端获取会话
- NestJS 校验 Supabase Auth 发放的 access token，并执行业务鉴权

### 认证规则

- 前台客户与后台管理员共用统一认证底座
- 后台访问通过角色字段控制
- 管理员角色禁止普通客户直接访问 `/admin`

说明：

- 当前项目不需要自建一套独立 JWT 认证体系
- 以 Supabase Auth 作为认证来源即可
- NestJS 只负责做 token 校验、用户识别与权限判断

## 9.5 对象存储

推荐选型：

- Supabase Storage

### 存储范围

- 商品图片
- Banner 图片
- 客户身份证资料
- 客户税号资料

### 安全要求

- 客户身份证 / 税号资料必须使用私有桶
- 后台按权限访问
- 记录上传者、订单关联、上传时间

## 9.6 部署

### 推荐正式部署架构

- Next.js：Vercel
- NestJS：独立 Node 容器服务
- PostgreSQL / Auth / Storage：Supabase

### 说明

你指定了 `NestJS` 作为正式后端。基于这一点，推荐的生产架构不是“所有东西都部署在 Vercel”，而是：

- Vercel 负责 Next.js 前端
- NestJS 单独部署
- Supabase 承担数据库、认证和对象存储

这样才能更稳地处理：

- 第三方物流 API 对接
- 后台订单处理
- 文件上传
- 后续计划任务 / 回调处理

## 13. 关键数据关系

### 物流订单

一票物流订单应至少具备：

- 主订单数据
- 头程信息
- 尾程信息
- 轨迹事件
- 客户资料引用

### 电商订单

一笔电商订单应至少具备：

- 商品项
- SKU 项
- 客户信息
- 可选的关联物流订单 ID

### 报价模型

报价至少要支持这些维度：

- 货物类型：B / C
- 国家
- 城市
- 重量区间
- 体积重规则
- 币种
- 生效时间

由于你后续会提供标准报价模板，因此建议数据库按“模板驱动 + 规则表”实现，不在第一版把计算逻辑写死在代码里。

## 14. 第三方 API 集成方案

第一版仅接入**一个固定海外尾程服务商**。

### 集成范围

- 创建尾程订单
- 获取尾程单号
- 拉取尾程轨迹

### 适配层设计

后端必须使用 provider adapter 模式，例如：

- `CarrierProvider`
- `CarrierCreateOrderDto`
- `CarrierTrackingMapper`

这样未来接第二个服务商时，不需要推翻物流主流程。

后台关键动作必须写日志：

- 审核通过 / 驳回

- 同步尾程单号
- 标记异常 / 签收
- 修改报价表
- 上架 / 下架商品
- 修改 Banner

日志字段至少包括：

- 操作人
- 操作时间
- 操作对象
- 操作前后摘要

## 20. 结论

修正后的正确方案应该是：

- 一个统一站点
- 两个独立前台模块
- 一个统一后台
- 物流模块优先按正式版落地
- 电商模块按轻量 MVP 上线
- 前端、后端、数据库、对象存储、认证一次性按生产级方案搭建

这份 PRD 可以直接作为下一阶段信息架构、数据库设计、接口设计和 UI 设计的基础文档。
